# Хранение полки в localStorage

## Контекст и постановка задачи

SRS требует, чтобы повторное открытие страницы показывало те же книги, если хранилище браузера доступно. Объём данных — полка одного человека. Нужно выбрать место, куда `LocalStore` пишет JSON.

Вопрос: где хранить полку между открытиями страницы?

## Драйверы решения

- Полка должна переживать закрытие вкладки (SRS п. 3.3.3).
- Специальных разрешений у читателя просить нельзя.
- Объём маленький: десятки книг, не медиафайлы.
- Повреждённая запись не должна затирать предыдущую полку.

## Рассмотренные варианты

- localStorage
- IndexedDB
- Файл на диске, который читатель выбирает сам при каждом запуске

## Итог решения

Выбранный вариант: «localStorage», потому что API синхронный, места хватает, и отдельное разрешение не нужно.

### Последствия

- Хорошо, потому что `LocalStore` читает и пишет одной парой `getItem` / `setItem`.
- Хорошо, потому что данные не уходят в сеть.
- Плохо, потому что очистка данных сайта стирает полку.
- Плохо, потому что квота браузера обычно около 5 МБ: для текста книг этого достаточно, для обложек — нет. Обложки в 0.2 и не входят.

### Подтверждение

Ключ `polka.shelf.v1` виден в инструментах браузера после «Сохранить». Повторное открытие файла показывает ту же полку. Некорректный JSON при загрузке не перезаписывает ключ.

## Плюсы и минусы вариантов

### localStorage

Строка по ключу в этом происхождении страницы.

- Хорошо, потому что просто и достаточно для JSON полки.
- Хорошо, потому что совпадает с формулировкой SRS п. 2.3.
- Плохо, потому что нет индексов и транзакций.

### IndexedDB

База в браузере.

- Хорошо, потому что держит больший объём и транзакции.
- Плохо, потому что для десятков записей избыточна.
- Плохо, потому что асинхронный API удлиняет первую итерацию.

### Файл на диске

Читатель каждый раз указывает файл.

- Хорошо, потому что копия лежит у человека, а не только в браузере.
- Плохо, потому что SRS не требует диалога открытия файла в 0.2.
- Плохо, потому что легко забыть, какой файл был последним.

## Дополнительная информация

Адресует REQ-FUNC-001, REQ-FUNC-002, REQ-FUNC-005 и надёжность из п. 3.3.3 SRS. Затрагивает представление SDD 004-information.
